# TURN, сигналинг — изолированный выпуск r1

База:9657faaaa59c31d3b3c2c489fc9a20a61e6fe5b0. Main и текущая публикация не меняются.
Работа ведётся в test/turn-signaling. TURN и federation должны выпускаться отдельными
коммитами; federation пока заблокирована, её готовность не заявляется.

Подготовленный TURN восстановлен из точного hosting source
91894da400a324213b24e41ee82a7f974a05ad09 (отдельная прежняя тестовая публикация).
Её прежние owner-reported физические PASS не являются испытанием нового артефакта
или доказательством каждого UDP/TCP endpoint по отдельности.

## Текущий клиент

Обычный URL использует all и прежний Google STUN. Пока отдельный TURN-кандидат
не получил физическую приёмку, он не добавляется автоматически в normal набор.
Включение конкретного кандидата — явный диагностический запуск:

- `?turn=express-udp&ice=relay` — один ExpressTURN/UDP кандидат, relay-only.
- `?turn=express-tcp&ice=relay` — один ExpressTURN/TCP кандидат, relay-only.
- После PASS этого кандидата повторить тот же `turn=...` с `ice=all`.

Владельческая пара передаётся частной ссылкой с percent-encoded fragment
`turn-user` и `turn-pass`, сразу удаляется через history.replaceState и остаётся
только в RAM вкладки. Username — строка без trim/Number; HMAC/TTL для этой пары
не применяется. Значения не в source, storage, логах и безопасном экспорте.
Reload требует повторного открытия исходной частной ссылки. Нет формы паролей.

Default STUN-only — явный временный статус приёмки, не обещание работающего TURN.
В relay нет скрытого перехода на direct; отсутствие кандидата/авторизации — ошибка.
Одиночный relay candidate недостаточен: нужен выбранный рабочий relay route.

Полный каталог — turn-candidates.json. Google дополнительные имена одного
провайдера и старые OpenRelay/ExpressTURN URI не активированы простым перечислением.
Публичные/архивные credentials не скопированы. API keys и static-auth secret
в JavaScript не помещаются.

PeerManager, ws-client и signaling сохраняются побайтно. RTCManager получает
конфигурацию и пассивное наблюдение готового PoC; нового direct→TURN recovery нет.
Профили, контакты и чаты используют отдельный namespace теста. Нет clear() или
удаления чужих SW/кэшей. Публичный сайт обязан иметь отдельный origin и audience
без OpenAI/ChatGPT авторизации; deployment success сам по себе не Android PASS.

## Почему federation ещё не готова

В текущей среде отсутствует требуемый whisper-cloudflare-signaling-test.zip.
Содержимое архива не выдумывается и новой реализацией под тем же названием не
подменяется. Доступы Cloudflare и независимого Node test hosting не подключены.
Нельзя выдавать production Render за отдельный тестовый Node.

Проверенный Node source LPYURA2/whisper-signaling:
43d3109da65b78adaeae978f18a1ef04666bf40d. Он имеет локальную Map presence,
join/ready и ownership guards, но не объединяет peers/сигналы между процессами.
Два WSS без моста не образуют федерацию. Для Worker требуется сверить модель
общего состояния/isolates по исходному архиву.

Далее нужны: авторизация межсерверного WSS, объединение local/remote presence,
session/boot generations и fencing адресата/отправителя, запрет replay SDP/ICE
после смены сессии, разрешение одного peerId на разных узлах и восстановление
presence после partition. Ни один узел не должен зависеть от выключенного узла
для приёма нового join. Bridge secret только runtime environment обоих серверов.

Клиентский handoff следует делать одним WSClient и одним текущим сокетом с тем
же peerId. Принятый PeerManager уже сохраняет healthy PC/DC при потере/смене
signaling; это подтверждено отдельной модельной проверкой. Старую устанавливаемую
операцию нельзя перепривязывать к новому socket. Native guards не доказывают
свежесть пакета, пришедшего через мост на новый socket: нужны server generations.

## Физическая приёмка владельцем

1. На двух Android без VPN открыть один test build, создать разные тестовые
   профили и контакты. Сначала подтвердить каждый тестовый WSS отдельно.
2. Подключить телефоны к разным реально работающим узлам. Проверить по3 полученных
   сообщения в каждую сторону. Затем отдельно выключить CF и Node, сохранив peerId,
   проверить новое установление и сохранность уже открытого DataChannel.
3. Проверить ExpressTURN сначала relay/UDP, затем отдельно TCP; на обоих устройствах
   нужны PCconnected, ICEconnected/completed, DCopen и активная selected pair с
   relay и типами обоих кандидатов, плюс реально полученные сообщения A↔B.
4. Повторить all для принятого кандидата и потерю/возврат сети. Не менять одновременно
   провайдера, транспорт, сеть и VPN. Записать время и экспорт обоих устройств.
5. При отказе копировать безопасную диагностику через30с и90с без reload. Обычные
   сырые SDP/profile логи не публиковать. Render, недоступный в целевой сети,
   не считать успешным резервом. Непроведённые проверки отмечать NOT RUN.

Модели, настоящий WSS, настоящий WebRTC и Android перечисляются отдельно.
Оригинальные M1–M55 в новой среде пока отсутствуют; старый отчёт не является повтором.
Установки production, main, действующего Render и облачной платной инфраструктуры
данным промежуточным этапом не выполняются.
